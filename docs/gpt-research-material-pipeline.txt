截至 `2026-03-16`，Anthropic 官方公开文档列出的 Sonnet 型号为 `claude-sonnet-4-20250514`，未查到公开的 “Claude Sonnet 4.6”；下面方案按可核实的 `Claude Sonnet 4` 设计。

---

**一、整体架构**

```text
React Upload UI
  -> FastAPI /uploads
  -> PostgreSQL 写入 document/job
  -> 文件落盘 S3/本地卷
  -> ARQ enqueue(document_pipeline)

ARQ Worker
  1. parse_pdf_job
  2. cartographer_job
  3. specialist_job(module_i) 并发
  4. examiner_job(module_i) 并发
  5. finalize_job

每一步:
  -> 更新 PostgreSQL 状态
  -> publish Redis channel: progress:{document_id}
  -> FastAPI SSE 订阅 Redis 并转发前端
```

建议目录：

```text
app/
  api/
  core/
  db/
  models/
  schemas/
  services/
    pdf/
    llm/
    pipeline/
    progress/
  workers/
  prompts/
```

**二、PDF解析选型**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `pymupdf4llm` | 原生输出 Markdown/JSON；保留布局信息；对标题、列表、代码块友好；适合直接喂 LLM | 表格精度一般；扫描件仍需 OCR | `主选` |
| `pdfplumber` | 基于字符级对象，表格提取和页面几何调试强 | 需要自己重建 Markdown 结构；速度和工程复杂度较高 | `辅选` |
| `PyPDF2` | 轻量、纯 Python、适合拆分合并元数据 | 官方文档已提示 `PyPDF2 is deprecated, please use pypdf`；文本抽取能力弱，不适合教学课件结构化 | `不选` |

落地建议：

- 默认先用 `pymupdf4llm.to_markdown()` 获取全量 Markdown。
- 同时保留 `to_json()` 结果，保存 bbox、page、block 级结构，供 Agent 1 判断章节边界。
- 如果检测到“表格密度高”或 `markdown/table` 缺失，则对对应页面调用 `pdfplumber.extract_tables()` 补强。
- 扫描 PDF 单独走 OCR 分支，不要指望 PyPDF2/pdfplumber 自动救活。

判定规则：

- 文本字数/页 < 30 且图片对象多：判定疑似扫描件
- 出现连续多页仅图片：切 OCR
- 出现课程目录/章节号/大标题字号差异：优先由 `pymupdf4llm + JSON layout` 划分模块

**三、任务队列选型：ARQ vs Celery vs Dramatiq**

| 方案 | 优点 | 缺点 | 适配度 |
|---|---|---|---|
| `ARQ` | 原生 `asyncio`；Redis 即可；和 FastAPI 协作最顺；轻量；重试简单 | 生态不如 Celery 大；复杂工作流需自己编排 | `最优` |
| `Celery` | 最成熟；生态最大；工作流能力强 | 配置更重；异步体验不如 ARQ 直接；对当前场景偏重 | 可用但过度 |
| `Dramatiq` | API 简洁；中等复杂度项目好用 | Python async 体验不如 ARQ 原生；对 FastAPI async 组合不如 ARQ 顺手 | 次优 |

结论：

- 你的链路是 `FastAPI + Redis + Claude API + SSE`，本质上是 IO 密集型异步任务，`ARQ` 最契合。
- 采用“1 个文档编排任务 + N 个模块任务”的 fan-out/fan-in 模式即可，不需要 Celery Canvas 的复杂度。

**四、核心流水线设计**

**状态机**

`uploaded -> parsing -> cartography_done -> specialist_running -> examiner_running -> completed`
失败状态分两层：

- 文档级：`failed`
- 模块级：`partial_failed`

**任务编排**

1. `parse_pdf_job(document_id)`
2. `cartographer_job(document_id, parsed_markdown, parsed_layout_json)`
3. `specialist_job(document_id, module_id)` 并发
4. `examiner_job(document_id, module_id)` 在对应 specialist 完成后触发
5. `finalize_job(document_id)`

**并发规则**

- Cartographer 串行
- Specialist 按模块并发，建议并发数 `3-5`
- Examiner 按模块并发，建议并发数 `5-8`
- 每模块独立事务，失败不影响其它模块

**五、进度推送：Redis Pub/Sub -> SSE**

Redis channel 规范：

- `progress:{document_id}`

事件格式：

```json
{
  "event": "module.completed",
  "document_id": "doc_123",
  "job_id": "job_456",
  "stage": "specialist",
  "module_id": "mod_03",
  "progress_percent": 58,
  "message": "模块3精讲已完成",
  "ts": "2026-03-16T10:15:30Z"
}
```

SSE 端点：

`GET /api/v1/documents/{document_id}/events`

前端监听事件：

- `document.status_changed`
- `module.started`
- `module.completed`
- `module.failed`
- `quiz.completed`
- `document.completed`

进度计算建议：

- PDF解析 10%
- Cartographer 15%
- Specialist 45%
- Examiner 25%
- 汇总入库 5%

**六、LLM调用规范**

实现建议：

- 模型：`claude-sonnet-4-20250514`
- 接口：Anthropic Messages API
- 输出：优先使用你要求的 `Structured Outputs(JSON Schema)`
- 兼容回退：若当前账号/区域未开通该能力，则 `JSON mode + 本地 jsonschema 校验 + 自动重试`

调用策略：

- Agent 1 输入全课件压缩文本
- Agent 2 输入“模块原文 + 模块计划 + 课程上下文摘要”
- Agent 3 输入“模块精讲 Markdown + 难点标签 + 陷阱点”

工程上必须加：

- `temperature` 低值：`0.1-0.3`
- `max_tokens` 分 Agent 单独限制
- schema 校验失败自动重试
- 语义校验：题目答案必须能在精讲里定位依据

**八、错误处理与重试**

原则：

- 单模块失败不影响整份课件完成
- 模块状态独立记录
- 文档结果允许 `completed_with_errors`

重试策略：

- `429 / 5xx / timeout / schema_validation_error`：自动重试
- 指数退避：`30s -> 120s -> 300s`
- 最大重试：
  - Cartographer：`2`
  - Specialist：`3`
  - Examiner：`3`

失败隔离：

- `specialist_job(mod_03)` 失败，只标记该模块 `failed`
- `examiner_job(mod_03)` 不执行，状态标记 `blocked_by_specialist_failure`
- 其它模块照常执行
- 汇总页展示“9/10 模块完成，1 模块失败，可人工重跑”

额外校验：

- page range 不得重叠错乱
- Specialist 输出长度过短则判 `quality_failure`
- Examiner 若答案不在选项中，直接重试
- 每道题必须至少引用一个 `skill_tag`

**十三、50页课件成本预估**

这里必须说明：这是 `推算`，不是官方定额。官方可核实的是 `Claude Sonnet 4` 价格：输入 `$3/MTok`，输出 `$15/MTok`。

按一份 50 页大学课件，较平衡估算：

- Cartographer：输入 `35k`，输出 `2k`
- Specialist 总计：输入 `45k`，输出 `22k`
- Examiner 总计：输入 `18k`，输出 `6k`

合计：

- 输入约 `98k tokens`
- 输出约 `30k tokens`

费用：

- 输入：`0.098 * $3 = $0.294`
- 输出：`0.030 * $15 = $0.45`
- 总计：约 **`$0.74 / 份`**

区间建议：

- 轻量课件：`$0.45 - $0.60`
- 常规课件：`$0.70 - $0.95`
- 公式密集/精讲更长：`$1.00 - $1.40`
